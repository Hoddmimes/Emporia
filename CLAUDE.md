# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Emporia is a marketplace system for trading commodities. Its focus is simplicity and pragmatism, so prefer straightforward solutions over elaborate abstractions.

The project is at an early stage. It is a multi-project Gradle build (group `com.hoddmimes`). The root project holds no code; it only aggregates the subprojects declared in `settings.gradle` (currently `Server`, `TestClient` and `Simulator`), which use the standard `src/main`/`src/test` layout.

## Server architecture

`Server` (package `com.hoddmimes.emporia.server`) is a single-process marketplace server: a Javalin 6 web server backed by MongoDB. It was ported from EmporiaX: the Javalin setup, the login/authorization mechanisms, the complete admin interface and its database layer, the instrument cache, the matching engine and the bulletin board. EmporiaX's IPMC/TCP messaging was not ported.

- `Server` (main class) takes `-config <file>` and optional `-mode normal|test` (default normal), reads the JSON config (`Server/emporia.json`), connects `Database`, loads the `InstrumentCache` and the `AuthorizationCache`, creates and starts the `BdxDistributor`, creates the `MatchingEngine`, creates and loads the `BulletinBoard`, starts the `AuctionScheduler` and the `MarketStateScheduler`, and starts `RestApi`. The config holds `sessionInactivityTime` (`mm:ss`), `database` (host/port/name) and `http_interface` (`root` web dir, `interface`, `http_port` and/or `https_port` + `ssl.cert`/`ssl.key` PEM paths, served via the Javalin SSL plugin, HTTP/1.1 only: `ssl.http2 = false` in `RestApi`, because over HTTP/2 Jetty offers browsers WebSockets over HTTP/2 (RFC 8441), which Javalin doesn't recognize as an upgrade (it looks for `Sec-WebSocket-Key`), so `/ws` failed in the browser with 1006 while HTTP/1.1 clients such as the TestClient worked). `Server/emporia.json` uses http 8080 and https 8443 with `./cert.pem`/`./key.pem` (relative to `Server/`); the PEM files are git-ignored (`*.pem`) and must never be committed, and the server does not start without them while `https_port` is set.
- `RestApi` builds the Javalin app and registers each class in `endpoints/` implementing `RestEndpoint` (one class per route for login/session, one `Admin*Endpoints` class per admin resource); shared dependencies reach endpoints through `RestApiContext`. New endpoints are added to the list in `RestApi.declareEndpoints`.
- Authentication is HTTP-session based. A `before("/api/*")` filter requires the session attribute `admin-user` for `/api/admin/*` and `user` for every other `/api/*` path, except the login/session paths listed in `RestApi.PUBLIC_PATHS`. After it, a `beforeMatched("/api/*")` handler puts the trading user on the Javalin context as a `SessionUser` record (userId, firm) for every matched non-admin `/api` request whose session has one; endpoints read it with `SessionUser.of(ctx)` (null without a trading user). Trading users log in at `/api/login` with firm, userId and password; admins at `/api/admin/login`. One browser session can hold both logins, so each logout removes only its own attributes (`RestApiContext.logout`).
- `Server/WebContent` is the static web root, ported from EmporiaX. The trading client UI sits at the root (`index.html`, `login.html`, `market-view.html`, `css/tr.css`, `js/tr-session.js`). `user-guide.html` is the end-user guide of the trading web interface (linked as Help in `market-view.html`'s header), with screenshots in `guide/` made by `tools/user-guide/make-screenshots.sh` (see below); update it, and rerun the script, when the trading UI changes. `api-doc.html` documents the public trading API (REST and WebSocket, not the admin API) for developers of trading applications; update it when a trading endpoint or bdx message changes. The admin UI is under `admin/` (`/admin` redirects to `/admin/login.html`), with every page and admin API call prefixed `/admin` and `/api/admin` so it doesn't clash with the trading UI. All admin pages are backed by endpoints. The trading `market-view.html` calls `/api/markets` and `/api/instruments?marketId=N` (`MarketEndpoints`, `InstrumentEndpoints`), which return only markets the user's firm is authorized for (403 for an unauthorized market). Authorizations are read from the `AuthorizationCache` (`RestApiContext.authorizedMarkets`, and `isAuthorized(firm, marketId)` for the single market checks), not from the login-time `markets` session attribute: it holds the `Authorization` collection in memory (per firm its market ids and whether it has `*`, which is expanded at lookup time, so a market created later is included), is loaded at startup and reloaded whole by `RestApiContext.reloadAuthorizations` after each admin change (authorization created or deleted, firm deleted), so admin changes apply at once; a change made directly in MongoDB applies only after a restart. Deleting a firm also deletes its authorizations (`Database.deleteFirm`). The page's `/ws` WebSocket (`bdx.BdxEndpoint`) pushes broadcast (bdx) messages, see below; the upgrade is rejected (401) unless the HTTP session has a trading user, the client may send `ping` (answered `pong`) and other client messages are ignored. `/api/logout` closes the WebSockets opened from that HTTP session, and so does the session timing out (an `HttpSessionListener` in `RestApi`). Jetty only detects timed-out sessions when its session housekeeper runs, so `RestApi` runs it every 30 s (or at the session timeout, if shorter) instead of Jetty's default 10 minutes. The server sends a WebSocket ping frame every 20 s (`BdxEndpoint.PING_SECONDS`, Javalin's `enableAutomaticPings`), which the browser answers by itself without running the page's JavaScript, so a page in a background tab, whose timers the browser throttles, stays connected; the WebSocket idle timeout is 2 minutes (`RestApi.WS_IDLE_TIMEOUT`, Jetty's default is 30 s), and the page's own 25 s `ping` is kept. The page retries a lost connection after 3 s, and at once when the tab becomes visible again (`visibilitychange`; phones suspend background tabs completely); after a reconnect it reloads the active view and shows popups for offers received while it was disconnected, since the server only resends its snapshot. The page lists the firm's authorized markets and, below them under their own heading in a teal color (`--bulletin` in `tr.css`), its bulletin markets (`/api/markets` and `/api/bulletin-markets`), each with a colored badge of its trading status (kept current by `MarketState`); the top menu button of the active view is highlighted. A continuous/auction market shows a dashboard: the price table on top (instrument, bid quantity, bid, ask, ask quantity, open, high, last, volume; a cell changed by a `PriceUpdate` flashes green when the value went up, red when it went down) and below it, side by side, the firm's resting orders in the market (`GET /api/orders?marketId=`, reloaded on each `OwnOrder` of the market; a double click asks whether to delete the order) and its trades in the market today, newest first (`GET /api/trades?marketId=`, reloaded on each `OwnTrade` of the market); a bulletin market shows its bulletins (`GET /api/bulletins?marketId=`, reloaded on each `Bulletin` message) instead of the price table. The page's Enter Order dialog follows the selected market: in a continuous/auction market it posts an order (`POST /api/orders`; instrument from the market's instruments, side, price and quantity required, an optional client account (`omni` if empty; remembered in the browser's `localStorage`, `emporia.clientAccount`, for the next order), price/quantity multiples of the instrument's `tickSize`/`lotSize`, market OPEN or PREOPEN), in a bulletin market a bulletin (`POST /api/bulletins`; free text instrument checked against the market's entries like `BulletinMarket.allows`, side optional (BUY, SELL or EITHER = no side, shown only for bulletins), price/quantity optional, market OPEN); it checks this before sending and shows the server's error with the HTTP status; an accepted order or bulletin closes the dialog and is confirmed by a short popup in the top right corner (`showToast`, closes after 8 s or on a click, at most 3 shown), and so is each `OwnTrade` ("Bought 100 ABB @ 101.50"; the instrument name is looked up, loading the market's instruments when needed), each `OwnBulletinTrade` ("Bulletin trade", "Sold 4 Brent Jan @ 80.00") and the end of one of the firm's own offers (`BulletinOffer` role OFFERER: "Offer rejected", "Offer expired", "Offer cancelled"; an accepted one shows its trade popup). A double click on a row of the price table opens the dialog for that instrument; on the bid it is prefilled as a SELL, on the ask as a BUY (trading against that side), with that side's best price and volume. A single click on a row of the price table (it waits for the double click time, so a double click only opens the Enter Order dialog) opens an order book dialog: a snapshot of the instrument's whole book (`GET /api/markets/{marketId}/orderbook/{instrumentId}`), bids and asks side by side per price level with the number of orders and the firm's own quantity, with Cancel and Refresh (a new snapshot); a click on any level opens the Enter Order dialog on top of it against that side's best price: on the bid a SELL at the best bid, on the ask a BUY at the best ask, with the best level's quantity. A click on a bulletin opens an offer dialog (`POST /api/bulletins/{bulletinId}/offer`): instrument, the bulletin and the offer's side (the opposite) shown; on a bulletin without a side (shown as EITHER) the offerer chooses BUY or SELL, required, price and quantity prefilled from the bulletin when it has them and required (quantity at most the remaining quantity), valid time in seconds (default 60) and an optional reference; not possible on one with a pending offer or while the market is not OPEN (a click on the firm's own bulletin opens the withdraw bulletin dialog instead). A bulletin with the firm's own pending offer is marked "(your offer)"; a click on it opens a withdraw offer dialog instead (the offer, a countdown, `DELETE /api/bulletins/{bulletinId}/offer`; closed when the offer ends meanwhile). The top menu's Bulletin Orders splits the main area horizontally: above, the firm's own bulletins in all its bulletin markets (`GET /api/bulletins`, the `own` ones), each with a Withdraw button (disabled while an offer is pending) that opens a withdraw bulletin dialog (`DELETE /api/bulletins/{bulletinId}`; a popup confirms it), which a click on the firm's own bulletin in a bulletin market opens too; below, the offers received on them that have not expired, with a countdown; a click on an offer opens an accept/reject dialog (`POST /api/bulletins/{bulletinId}/response`). It is reloaded on each `Bulletin` and `BulletinOffer` message; selecting a market leaves it. The top menu's My Orders shows the firm's resting orders (all its users') in all markets, or in the market chosen in its market list (`GET /api/orders`, `?marketId=`; each order has `orderTime`, its entry time in ms), reloaded on each `OwnOrder`; a double click on an order asks whether to delete it (`DELETE /api/orders/{orderId}`). The top menu's My Trades shows the firm's trades in all markets for one day: today's by default (`GET /api/trades`, reloaded on each `OwnTrade` and `OwnBulletinTrade`), or the day entered as `yyyy-MM-dd` in its date field (with previous/next/today buttons; `GET /api/trades?date=`). The dashboard's orders and trades, My Orders, My Trades, the firm's bulletins in Bulletin Orders and the delete order dialog show each order's, bulletin's or trade's client account (Account); the Enter Order dialog (also for bulletins) and the offer dialog have a Client account field, prefilled with the last one used. The top menu's My Portfolio shows `GET /api/portfolio` (market, instrument, client account, position, bought, sold, last price, value, total value; its Account selector shows the positions per account (default; Sort by Instrument or Account), added up per instrument (Total per instrument), or one account's), reloaded on each `OwnTrade` and `OwnBulletinTrade` and revalued on each `PriceUpdate` with a new last price and each `BulletinTrade`; the trades and portfolio views show bulletin trades and positions with their market in the bulletin color, a bulletin trade with "bulletin <id>" as its order id. A `BulletinOffer` OFFERED with role OWNER (sent to every client of the bulletin owner's firm) shows a popup in any view ("New bulletin offer", with a countdown; Answer opens the view and the response dialog), removed when the offer is answered, expires or is cancelled; it also shows a desktop notification (Notifications API: https or localhost only, permission asked on the first click on the page; clicking it opens the offer). The page only uses `Chat` (popup, Chat view), `PriceUpdate`, `MarketState` (keeps the markets' `tradingStatus` current), `Bulletin`, `BulletinOffer` (popups, view reloads), `OwnOrder` (My Orders and dashboard reload), `OwnTrade` (trade popup; portfolio, today's trades and dashboard reload), `OwnBulletinTrade` (trade popup; portfolio and today's trades reload) and `BulletinTrade` (portfolio revaluation) and ignores the other message types; when a market is selected it also reads `GET /api/markets/{marketId}/prices`, used only for instruments that have no WebSocket prices yet.
- Broadcasts live in package `bdx` (EmporiaX's topic scheme and order book events, without its IPMC transport). `BdxMessage` is a JSON object starting with `type`, `topic` (`/<type>/<marketId>/<instrumentId>`, or `/<type>/<marketId>` for market messages), `marketId` and `instrumentId`, followed by its fields; prices and quantities are in display units (unlike the REST API's scaled longs). `BdxDistributor` sends a global message (`BdxMessage.global`: topic `/<type>`, no `marketId`; used for `Chat`) to every client, a public message to every client whose firm is authorized for the market (resolved when the client connects and replaced by `BdxDistributor.updateAuthorizations` after an authorization change or a market or bulletin market created or deleted (`RestApiContext.refreshClientAuthorizations`), which sends a client the `PriceUpdate`/`MarketState` snapshot of each market it gained and logs the change) and a private one only to the clients of its firm; it keeps the latest `PriceUpdate` per instrument and `MarketState` per market and sends them to a client when it connects. `publish` only queues a message; the distributor is a thread (`WsPublisher`, started by `Server`) that sends the queued messages, so the matching engine never waits for the clients. The WebSocket sends are asynchronous (Jetty queues them per session), so a slow client doesn't hold up the others; a client with more than 10000 unsent messages is disconnected (1008). Every connection is logged at info level by the distributor when it is added and removed (`addClient`/`removeClient`/`closeClients`): an id `ws1`, `ws2`, ... (restarting with the server) ties the two lines together, with user, firm and remote address (the first `X-Forwarded-For` address behind a proxy, else the peer's); the disconnect line has the close code and reason (`BdxDistributor.closeDescription`, e.g. `code 1001 (going away)`), `closed by the server: Logged out`/`Session expired` or `connection error: ...`, the connection time and the number of broadcast messages sent. A refused connection (no logged-in trading user) is logged by `BdxEndpoint`/`webapp.BdxWebSocket`. Unit tests don't start the thread and call `dispatchQueued()` instead. Types: `PriceUpdate` (a full snapshot after each book change: best bid/ask price and volume, open, high, last, traded volume; JSON `null` clears a value), `MarketState` (published by the distributor itself on the cache's market state changes), `Trade` (anonymous: no firms), the anonymous order book events `AddOrder`/`ModifyOrder`/`RemoveOrder` (orderId, side, price, remaining quantity and the book's `seqNo`; a partial fill of a resting order is a `ModifyOrder`, a fully filled one a `RemoveOrder` with quantity 0; an incoming order that matches completely never rests and has no event), and the private `OwnOrder` (the same plus `event` ADDED/MODIFIED/REMOVED and `userRef`) and `OwnTrade` (one per side, to that side's firm, with side, orderId and `userRef`). The matching engine publishes all of them except `MarketState` from its orderbook callbacks. The bulletin board publishes market messages (`/<type>/<marketId>`, see below): public `Bulletin` and `BulletinTrade`, private `OwnBulletin`, `BulletinOffer` and `OwnBulletinTrade` (`BdxMessage.forFirm(type, marketId, firm)`).
- `Database` wraps MongoDB collections `Firm`, `User`, `Markets`, `Instruments`, `BulletinMarkets`, `Bulletins`, `Authorization` (firm → market, `*` = all markets, bulletin markets included) and `Admin`, plus `Trades` and `BulletinTrades` (see below); MongoDB is the master store. A new market's `marketId` is the highest existing one + 1, over markets and bulletin markets together (`RestApiContext.nextMarketId`, so an authorization or bdx topic names one market), so a market can only be deleted once it has no orders and no instruments (a bulletin market once it has no bulletins); deletes are refused with 409. The admin can clear a market first: `DELETE /api/admin/markets/{id}/orders` (`MatchingEngine.deleteAllOrders`) and `DELETE /api/admin/bulletin-markets/{id}/bulletins` (`BulletinBoard.deleteAllBulletins`, state DELETED, a pending offer gets `BulletinOffer` event CANCELLED) delete everything in the market, of every firm, in any market state, overruling the authorization and trading status rules; the market and bulletin market pages have Delete All Orders / Delete All Bulletins buttons (otherwise a new market could reuse its id and inherit them). An `instrumentId` is a long with the `marketId` in the high 32 bits and a per-market sequence (from 1) in the low 32 bits; it is stored as a string. Passwords are stored as SHA-512 hex. A default admin `Admin`/`changeit` is created when the `Admin` collection is empty.
- `InstrumentCache` holds all markets and instruments in memory (ported from EmporiaX, without IPMC). `Server` loads it from MongoDB at startup and it is reached through `RestApiContext.instrumentCache`. Read markets and instruments from the cache wherever possible: the trading endpoints, market-existence checks, the `*` authorization expansion and new `marketId`/`instrumentId` allocation all use it. Only the admin list/get endpoints read MongoDB, because the admin pages need each document's `mongoId`. Every market/instrument write goes to MongoDB first; the endpoint then re-reads the document and calls `putMarket`/`putInstrument` (or `removeMarket`/`removeInstrument`), which notify `MarketCallbacks`/`InstrumentCallbacks` subscribers.

- The matching engine lives in package `me` (ported from EmporiaX's `me` module without IPMC; the bulletin board is in package `bulletin`; EmporiaX's generated request/response messages are replaced by the records `AddOrderRequest`, `OrderResponse` and `AuctionResult`). `MatchingEngine` keeps one `Orderbook` per instrument, created on first order: a CONTINUOUS book matches incoming orders immediately in price-time priority at the resting order's price, an AUCTION book only collects orders until `AuctionScheduler` triggers an uncross at one clearing price (max volume, then min imbalance, then closest to the last price, otherwise the lowest candidate). `AuctionScheduler` arms auctions at startup for the AUCTION markets in the cache, from each market's `open`/`close`/`auctionInterval`/`randomAuctionInterval`; markets or instruments added later need a restart. Prices and quantities are longs scaled by `MatchingEngine.SCALE` (100000), checked against the instrument's `tickSize`/`lotSize`. Orders and books are in memory only and are lost on restart. Each trade is also stored in MongoDB's `Trades` collection, durably and before anyone hears of it, so no trade is lost on a host failure: the engine doesn't publish or store anything itself but queues its bdx messages and trades, in order, in `me.TradePersister`, whose thread stores each batch of trades with one journaled write (`Database.saveTrades`, `insertMany` with `WriteConcern.JOURNALED`, so one fsync covers all trades of the batch: group commit; about 2 ms per fsync on hoddmimes) and only then publishes the batch's messages in their order (so a book's events keep their `seqNo` order, and the web page's portfolio reload on `OwnTrade` finds the trade); `addOrder`, `modifyOrder` and `triggerAuction` wait after leaving the order book's lock until a trade they made is stored and published (`MatchingEngine.durable`), so an order response never reports a trade that isn't on disk, while other orders are matched meanwhile; a failed write is retried every second, holding back the broadcasts and those responses; `Server.stop()` stores what is queued (`MatchingEngine.stop`). REST reads of the engine's memory (today's trades, prices, order book) can show a trade in the few ms before it is stored. The documents (`Database.saveTrade`; ids as hex strings, prices/quantities scaled, `tradeTime` as a `yyyy-MM-dd HH:mm:ss.SSS` string in server local time; indexed on `tradeTime`, `_id` and on `buyAccount`/`sellAccount` each followed by `tradeTime`, `_id`, created at connect by `Database.createIndexes`, which serve the day range, a firm's trades and the latest first sort), and the engine reloads today's trades at startup (`Database.fromTradeDocument`) and replays them, oldest first, into the open/high/last/volume statistics of their order books (`MatchingEngine.restoreTrades`, creating the books, which stay empty of orders), then publishes a `PriceUpdate` per instrument, so the bdx snapshot and `/prices` show the day's prices after a restart. `MatchingEngine` takes the `Database`; the unit tests pass null, which skips storing and reloading. Each order book has its own lock (`synchronized` on the `Orderbook`, held by `MatchingEngine` around every call into the book; the book itself is not thread-safe), so orders in different instruments are matched in parallel on the request threads and those in one instrument one at a time; the shared state is thread-safe: the book map (`ConcurrentHashMap`, a book created with `computeIfAbsent`), an index of resting orders (order id → instrument, kept by the `orderAdded`/`orderRemoved` callbacks, so a modify or delete goes straight to its book and checks the order again under the book's lock) and today's trades (a synchronized list); a request spanning several books (a firm's or a market's orders, a market's prices, `deleteAllOrders`, the uncross at open) locks one book at a time, so it is no atomic snapshot of them all. The trading status is checked under the book's lock, which the uncross at open also takes after the status changed to OPEN, so an order is either uncrossed or matched at once. An order's account is its firm, and a firm can only see, modify and delete its own orders. An order is only accepted (added or modified) while its market's `tradingStatus` is OPEN or PREOPEN and its instrument is not SUSPENDED (instruments are ACTIVE or SUSPENDED; the bulk load stores any other status, such as EmporiaX's OPEN, as ACTIVE), checked in `MatchingEngine` against the cache before the order reaches a book; deleting is allowed in every market state except CLOSED (also while the instrument is SUSPENDED). In PREOPEN orders are only put in the book, without matching; `MatchingEngine` subscribes to the cache's market state changes and, when a market changes to OPEN, uncrosses its continuous books once at a single clearing price (same algorithm as the auctions) before continuous matching takes over.
- Order entry (`OrderEndpoints`, `TradeEndpoints`): `POST /api/orders` (`instrumentId`, `side` BUY/SELL, `price`, `quantity`, optional `userRef` and `clientAccount`), `PATCH /api/orders/{orderId}` (`quantity`, optional `price`/`userRef`; a missing price or userRef keeps the order's current one, and a modify that increases the quantity or moves the price towards the other side replaces the order with a new `orderId`, returned in the response; a `clientAccount` field is rejected with 400, the order keeps its own), `DELETE /api/orders/{orderId}`, and the firm's own `GET /api/orders` and `GET /api/trades` (optional `?marketId=` and/or `?instrumentId=`; `GET /api/trades` also takes `?date=yyyy-MM-dd`, which reads that day's trades from the database instead of today's from the engine, 400 for an invalid date). Public market data (`MarketEndpoints`, firm must be authorized for the market, 403; unknown market 404): `GET /api/markets/{marketId}/trades` (today's trades in the market, oldest first, anonymous; optional `?instrumentId=`) `GET /api/markets/{marketId}/orderbook/{instrumentId}` (`MatchingEngine.getOrderbook`: the instrument's whole book aggregated per price level, `bids` and `asks` best first, each level `price`, `quantity`, `orders` and `own` = the firm's quantity at the level, so it is anonymous otherwise; plus open/high/last/volume and the snapshot `time`; 404 for an instrument not in the market) and `GET /api/markets/{marketId}/prices` (a snapshot per instrument of the market, sorted by name, with the `PriceUpdate` fields scaled like the rest of the API; JSON null where there is no value, also for instruments without an order book yet). Trades are listed from the engine's memory (today's, reloaded at startup); the firm's bulletin trades of the same day (today's or `date`'s, from `BulletinTrades`, filtered by `marketId`, none with `instrumentId`) are listed apart in `bulletinTrades` (free text `instrument`, `bulletinId`, `user` and `ref`, the firm's `userRef` or `offerRef`). Holdings (`PortfolioEndpoints`): `GET /api/portfolio` returns the firm's position per instrument and client account (`clientAccount`; `omni` for trades stored without one) from all its stored trades of every day (`Database.listTradesByFirm` with no date; bought minus sold, a trade with itself nets 0 within one client account and moves the position between two different ones, positions of 0 left out), with `bought`, `sold`, `lastPrice` (today's from the engine, `MatchingEngine.getLastTradePrice`, otherwise the latest stored trade's, `Database.lastTradePrice`; null if none) and `value` = position × last price (scaled, null without a price), sorted by market, instrument and client account, plus `totalValue`; bulletin trades give positions of their own per bulletin market and instrument text (`bulletin` true, `instrumentId` null), also per client account, valued at the latest bulletin trade price of that instrument text in that market (`Database.lastBulletinTradePrice`). The firm comes from the session; adding or modifying requires the firm to be authorized for the instrument's market (403), another firm's order is reported as not found (404), and engine rejections return 400 with `{"error":...}`. Order ids are hex strings. The `clientAccount` is the firm's own account for an order (a client, a trader's book), free text: 1–32 letters, digits, spaces or `. _ - /` after trimming (`OrderEndpoints.CLIENT_ACCOUNT`; case-sensitive, 400 otherwise); left out or empty it is the default account `omni` (`AddOrderRequest.DEFAULT_CLIENT_ACCOUNT`, set by the record's constructor, so every order has one); the order carries it (`Order.getClientAccount`, kept when a modify replaces the order) to its trades, one per side (`Trades` fields `buyClientAccount`/`sellClientAccount`; absent in documents stored before client accounts, read as `omni` by `Database.clientAccountOf`); it is private: in `OwnOrder`/`OwnTrade`, `GET /api/orders` and `GET /api/trades`, never in the public bdx messages. Bulletins and offers have a client account too (see the bulletin board).

- The bulletin board (package `bulletin`, ported from EmporiaX's `BulletinBoard`/`BulletinManager`/`BulletinEntry`, without IPMC) holds informal OTC bulletins in the bulletin markets. Bulletin markets are kept apart from the continuous/auction markets: collection `BulletinMarkets` (`BulletinMarket` record: `marketId`, `name`, `description`, `tradingStatus` OPEN/CLOSED/SUSPENDED, `open`/`close` times (required), `instruments`, `maxOrderTime` as `"hh:mm"`, hours may exceed 24, e.g. `"168:00"`), held by the `BulletinBoard` instead of the `InstrumentCache`, so the `AuctionScheduler` and matching engine never see them. The `MarketStateScheduler` (which takes the `BulletinBoard`) drives their status from `open`/`close` with the same rules as the other markets (no pre-open; closed at startup in normal mode, opened in test mode; SUSPENDED is set and lifted manually in the admin interface and never changed by the scheduler), writing through `Database.setBulletinMarketStatus` and `BulletinBoard.putMarket`. `Markets` only accepts the types CONTINUOUS and AUCTION. A bulletin market's `instruments` list (at least one entry) says what bulletins may be added for: an entry is a literal name matched exactly (case-sensitive), or a regular expression between slashes (`/Brent.*/`) that must match the whole instrument text. Admin: `AdminBulletinMarketEndpoints` (`/api/admin/bulletin-markets`, pages `bulletin-markets.html`, `create-bulletin-market.html`, `bulletin-market.html`), writing MongoDB first and then `BulletinBoard.putMarket`/`removeMarket`; `putMarket` publishes a `MarketState` for a new market and on each status change. `BulletinBoard` is one object for all bulletin markets (public methods `synchronized`); every bulletin is stored in `Bulletins` (`Database.saveBulletin`/`deleteBulletin`, without a pending offer) and reloaded by `BulletinBoard.load()` at startup, since bulletins can stay in the book for days. A bulletin gets `expiresAt` = add time + the market's `maxOrderTime` (a later change of `maxOrderTime` applies to new bulletins only) and is then removed with state EXPIRED, a pending offer expiring with it; bulletins that expired while the server was down are removed at load. `BulletinBoard` takes the `Database` (null in the unit tests: nothing stored) and publishes through a `Consumer<BdxMessage>` (`BdxDistributor::publish` in `Server`, a list in the tests). A bulletin has `marketId`, a free text `instrument` (no instrumentId), an optional `side` BUY/SELL (null = no side: the owner will buy or sell, the offering firm chooses), optional `price`/`quantity` (0 = not given) and `userRef`; it is never matched. Another firm makes an offer (`side`: on a bulletin with a side the opposite one, optional in the request and checked; on one without a side BUY or SELL, required; stored with the offer as `offerSide`, and the owner's side in the trade is its opposite; price, quantity up to the remaining quantity, optional `offerRef`, `validTime` seconds, default 60); a bulletin holds at most one pending offer. The owner's firm accepts it (a trade at the offer's price and quantity; the remaining quantity drops, and the bulletin is removed when it reaches 0 or had no quantity) or rejects it; an unanswered offer expires (a timer thread `BulletinExpiry`). Accounts are firms, as for orders: any user of the owner's firm may withdraw or answer, another firm's bulletin is reported as not found, and a firm can't offer on its own bulletin. Withdrawing is not allowed while an offer is pending. The offering firm may withdraw its pending offer (any user of the firm, in any market state; `BulletinOffer` event CANCELLED to both firms, the bulletin is ACTIVE again). Adding, offering and accepting require the market to be OPEN; withdrawing and rejecting are always allowed. Each bulletin trade is stored in MongoDB's `BulletinTrades` collection, journaled and before its bdx messages are published (`Database.saveBulletinTrade`, kept apart from `Trades`, whose documents are replayed into the order books at startup): `tradeNo`, `bulletinId`, `marketId`, `instrument`, `price`/`quantity` scaled, `tradeTime` as in `Trades`, and `buyAccount`/`buyUser`/`buyRef`/`buyClientAccount`, `sellAccount`/`sellUser`/`sellRef`/`sellClientAccount` (the refs are the bulletin's `userRef` and the offer's `offerRef`, the client accounts the bulletin's and the offer's). A bulletin (`POST /api/bulletins`) and an offer (`POST .../offer`) take an optional `clientAccount` like an order (`OrderEndpoints.clientAccountOf`; default `omni`, also for bulletins stored before client accounts): stored with the bulletin (`Bulletins` field `clientAccount`) and the pending offer (`offerClientAccount`, in memory), private: the owner sees the bulletin's in `GET /api/bulletins`, `OwnBulletin` and its `BulletinOffer` (role OWNER), the offering firm its offer's (the offer's `clientAccount`, `BulletinOffer` role OFFERER), each firm its own side's in `OwnBulletinTrade` and `GET /api/trades` (`bulletinTrades`). Endpoints (`BulletinEndpoints`, firm must be authorized for the market, 403 otherwise): `GET /api/bulletin-markets` (the firm's authorized bulletin markets with their hours, instruments and `maxOrderTime`), `POST /api/bulletins`, `GET /api/bulletins` (optional `?marketId=`; everyone sees the public fields, the owner also `user`/`userRef` and a pending offer, the offering firm its own offer; an offer has its `side`), `DELETE /api/bulletins/{bulletinId}`, `POST /api/bulletins/{bulletinId}/offer`, `DELETE /api/bulletins/{bulletinId}/offer` (the offering firm withdraws its pending offer; 404 if it has none), `POST /api/bulletins/{bulletinId}/response` (`accept` true/false). Prices and quantities are scaled longs in REST, display units in bdx. Bdx messages: public, anonymous `Bulletin` (`event` ADDED/UPDATED/REMOVED, `state` ACTIVE/OFFER_PENDING/TRADED/WITHDRAWN/EXPIRED/DELETED, `remainingQuantity`, `expiresAt`; price/quantity null when not given) and private `OwnBulletin` (the same plus `user`, `userRef`) to the owner's firm on every change; private `BulletinOffer` (`event` OFFERED/ACCEPTED/REJECTED/EXPIRED/CANCELLED (CANCELLED: withdrawn by the offering firm or deleted by the admin), `role` OWNER with `userRef` or OFFERER with `offerRef`, the offer's side, price, quantity and `expiresAt`) to both firms; for a trade a public, anonymous `BulletinTrade` and a private `OwnBulletinTrade` (side, `userRef` or `offerRef`) to each side's firm. The firms are never told who the other side is. Bulletins are not part of the snapshot sent on connect; a client reads them with `GET /api/bulletins`.
- Chat (`ChatEndpoints`) between the trading users of all firms: `POST /api/chat` (`text` required, at most 512 bytes in UTF-8 after stripping leading/trailing white space; optional `tag`, at most 64 bytes, empty if not given; 400 otherwise) stores the message in MongoDB's `Chat` collection (`chatId` (an ObjectId's hex), `time` as `yyyy-MM-dd HH:mm:ss.SSS` like `tradeTime`, `firm`, `user`, `text`, `tag`; indexed on `time`, `_id`), journaled (`Database.saveChatMessage`), then publishes a global `Chat` bdx message (`chatId`, `time` in epoch ms, `firm`, `user`, `text`, `tag`) to every connected trading client, and answers 201 with the same fields. `GET /api/chat` returns the stored messages oldest first: `date` (yyyy-MM-dd, default today) = on and before that day, optional `fromDate` = from that day (both = one day), optional `tag` = tag contains the text (case-insensitive, matched literally: `Database.escapeRegex`), `limit` (1..5000, default 1000) = the latest ones, with `more` true when older ones were left out (`Database.listChatMessages`). The web page's top menu Chat view shows the messages from the day in its From field (default today) up to now (`fromDate`; a tag filter), with each message's time, user, firm and tag; a matching `Chat` message is added at the bottom; below the list a message is sent with an optional tag (Enter sends, Shift+Enter a new line, a UTF-8 byte counter). Every `Chat` message from someone else (not the same firm and user) shows a popup in any view, centered below the top menu (apart from the other popups in the top right corner) for 12 s (`CHAT_TOAST_MS`; the others 8 s, `TOAST_MS`).
- `MarketStateScheduler` drives each market's (and bulletin market's) `tradingStatus` from its market hours (server local time): on weekdays PREOPEN at `preOpenTime` (if set), OPEN at `open`, CLOSED at `close`; on Saturdays and Sundays markets stay CLOSED (only the close transition applies). It checks once a second whether a transition time was passed, reading the hours from the cache, so edits and new markets apply without a restart and a manual change in the admin interface stands until the next scheduled time. It writes through `Database.setMarketStatus` and `InstrumentCache.putMarket`, so OPEN triggers the matching engine's opening uncross. SUSPENDED is manual and never changed by the scheduler, in any mode. At startup in normal mode every OPEN or PREOPEN market is set to CLOSED (so a restart or redeploy during market hours comes up closed; the open time has passed, so it stays closed that day) and has to be opened manually in the admin interface; `-mode test` overrides the scheduler: every market that is not SUSPENDED is set to OPEN at startup and the market hours are not applied (no transitions). `openAuctionTime` is not used, and the `AuctionScheduler` is independent of it.

Run it with `./gradlew :Server:run`, which uses `Server/` as working directory and `-config emporia.json` (for test mode: `./gradlew :Server:run --args="-config emporia.json -mode test"`); MongoDB must be running on the configured host. Logging is Log4j2, writing to the console and `server.log`. Every `/api` request gets an id from a counter (`r1`, `r2`, ..., restarting with the server), set in a `before` handler registered ahead of the auth filter: it is put in the Log4j `ThreadContext` under `rid`, so every line logged on the request's thread (endpoint, matching engine, database) shows it via `%X{rid}` in the pattern (`[]` outside requests and on other threads, such as the `WsPublisher`), and it is returned in the `X-Request-Id` response header; the last `after` handler removes it, since Jetty reuses its threads. Every `cLog.trace(...)` call is wrapped in `if (cLog.isTraceEnabled()) { ... }`, so its arguments are not built when trace is off; keep to that for new trace logging. The log configuration: `./gradlew :Server:run` and the IntelliJ `Server` run configuration pass `-Dlog4j2.configurationFile` pointing at `Server/log4j2.xml`; without it (e.g. tests) the built-in `src/main/resources/log4j2.xml` is used.

Packaging (`./gradlew :Server:build` or the single tasks): `shadowJar` makes the fat jar `Server/build/libs/Server-<version>-all.jar` (Shadow plugin, service files merged), run with `java -jar Server-<version>-all.jar -config emporia.json [-mode test]`; the config's `root` must point at a WebContent directory. `war` makes `Server/build/libs/emporia.war` for Tomcat 10.1+ (Jakarta EE): the pages from `WebContent` at its root, `src/war/WEB-INF/web.xml` (declares the listener; `<absolute-ordering/>` keeps the Jetty jars' ServletContainerInitializers from running in Tomcat; the Jetty servlet-api jar is left out). Its file name gives the context path: `emporia.war` is served at `/emporia`. The pages and their scripts use relative URLs (`api/...`, in `admin/` `../api/...`; the WebSocket URL is built with `new URL('ws', location.href)`), and the server matches routes below the context path (`config.router.contextPath`, `RestApi.apiPath`), so the same pages work at the root (fat jar) and below a context path; keep new URLs relative. The WAR has its own `log4j2.xml` (`src/war/resources`, logs to Tomcat's `logs/emporia.log`). The config file can be given in a context descriptor, e.g. `conf/Catalina/localhost/emporia.xml` with `<Parameter name="emporia.config" value="..."/>`, so Tomcat needs no restart. `webapp.EmporiaWebApp` (a `ServletContextListener`) starts the same `Server` object as `main` (`Server` holds the components; `Server.stop()` stops its threads and closes MongoDB at undeploy), reads the config file from `emporia.config` (context parameter, system property, e.g. `CATALINA_OPTS=-Demporia.config=/path/emporia.json`) or `EMPORIA_CONFIG`, and the mode from `emporia.mode`/`EMPORIA_MODE`; the config's `http_interface` is not used, Tomcat does ports and HTTPS. It registers the REST API as a servlet (`RestApi.createServlet()`: Javalin's `JavalinServlet` on `/api/*`, `/admin`, `/admin/`, without Jetty settings) and `/ws` as a Jakarta WebSocket endpoint (`webapp.BdxWebSocket`, since Javalin's WebSockets need Jetty): same behaviour as `bdx.BdxEndpoint` (session check, ping/pong, 20 s ping frames, 2 min idle timeout, closed on logout and session timeout), except that a connection without a trading user is opened and closed at once with 1008 instead of being refused with 401; Tomcat allows one asynchronous send at a time, so each connection has a send queue. A Jakarta endpoint can't see the client's address, so `EmporiaWebApp` maps a filter on `/ws` ahead of Tomcat's WebSocket filter that adds it to the upgrade request as the header `X-Emporia-Remote-Address` (replacing any such header from the client). The build version and date: the version is `V<version>-<build>` (e.g. `V1.0-001`) from `Server/version.properties`: `version` is the main version, changed by hand only when the user says so; `build` is increased by one by each Gradle run that builds the WAR or the fat jar (`gradle.taskGraph.whenReady`, so `./gradlew build` counts once; compiling or testing does not count; the file is meant to be committed). The task `generateBuildInfo` writes `emporia-build.properties` (that version, build time `yyyy-MM-dd HH:mm`) to `build/generated/buildinfo`, a resource directory; `BuildInfo` reads it ("unknown" without it), the server logs it at startup and the public `GET /api/version` returns it, shown under the form on both login pages.

## Test client

`TestClient` (package `com.hoddmimes.emporia.testclient`) is a load/test program that uses only the REST API (Gson + `java.net.http`, no dependency on `Server`). It reads a JSON file (`-config <file>`, example `TestClient/testclient.json`) with `url`, optional `trustAllCertificates` (accept any HTTPS certificate, for the expired/self-signed ones) and `verbose`, and an array of `sessions`. Each session has `firm`, `user`, `password`, `repeat`, `txRate` (directives per second, 0 = unthrottled) and `directives`: `AddOrder` (`instrument` name or `instrumentId`, `side`, decimal `price`/`quantity` scaled by 100000 for the API, optional `userRef` and `clientAccount`; the `orderId` from the response is remembered under the `userRef`) and `DeleteOrder` (`userRef` of an earlier AddOrder; deletes that order by its `orderId`). Sessions run concurrently, each with its own HTTP session; a summary per session is printed (transactions sent/OK/failed and the average, median and 96% interval (2nd–98th percentile) of the transaction times) and the exit code is 2 if anything failed. With `-bdx true` (the default; `-bdx false` turns it off) each session opens a WebSocket to `/ws` with its own HttpClient (so it carries the session cookie) after logging in, waits for the reply to a first `ping` (the server answers it only after registering the connection, so no broadcast is missed), counts the broadcast messages it receives and, with `verbose`, prints each one (`[session] bdx: {...}`), sends `ping` every 25 s, and closes it 500 ms after its last directive; there is no subscription step, the server sends everything the firm may see. No session sends a transaction before all sessions have logged in and set up their WebSocket (a shared latch; a session whose setup fails still releases it). Run it with `./gradlew :TestClient:run` (uses `TestClient/testclient.json`) or `./gradlew :TestClient:installDist` and `TestClient/build/install/TestClient/bin/TestClient -config <file>`.

## Simulator

`Simulator` (package `com.hoddmimes.emporia.simulator`) simulates market activity through the REST API and the `/ws` feed (Gson + `java.net.http`, no dependency on `Server`), as one trader, until it is stopped. It reads a JSON file (`-config <file>`, example `Simulator/simulator.json`, format in the `Simulator` class Javadoc) with `url`, optional `trustAllCertificates`, `firm`/`user`/`password`, `txRate`, and the entries:

- `continuous`: per instrument of a CONTINUOUS market (`instrument`, optional `market` if the name is in several markets) an order flow (`ContinuousSimulator`). The top-level `txRate` is the number of transactions (order adds or deletes) generated and sent per second in total; each transaction is one step of an instrument chosen at random, so with n instruments each gets `txRate`/n per second on average (one task, so the steps never overlap: a step slower than 1/`txRate` lowers the rate). Bulletins are not counted in `txRate`. Each step reads the simulator's own orders in the instrument (`GET /api/orders`; the depth counts only its own orders, the API has no full book) and the best prices, then adds a passive order on a side below `minDepth`, deletes one on a side above `maxDepth`, or otherwise adds or deletes at random within the limits. Passive prices are `midPrice` minus/plus a random amount from one tick up to `maxPriceDeviation`, never crossing the other side; volumes random between `minVolume` and `maxVolume`; an optional `clientAccount` is sent with each of the instrument's orders (and per `bulletins` entry with each bulletin); both rounded to the instrument's tick and lot size. Every `tradeRate`-th order is a matching order instead, at the best opposite price and at most its volume, so it trades without resting.
- `bulletins`: per bulletin market (`market`) and free text `instrument` one bulletin at a time (`BulletinSimulator`): created after a random 10..`timeToCreate` seconds and withdrawn after a random 10..`timeToLive` seconds, then the next. `side` is optional (BUY, SELL or NONE for a bulletin without a side; random among the three if absent), `midPrice`/`maxPriceDeviation` and `minVolume`/`maxVolume` too (no price or quantity without them). A bulletin with a pending offer is withdrawn when the offer is gone (retried every 5 s); offers are not answered.

Every event is printed with a timestamp: CREATE, MATCH, DELETE, TRADE (from `OwnTrade`, also for its resting orders hit by others), BULLETIN CREATE/DELETE/GONE/OFFER/TRADE/EXPIRED, ERROR (the same error is printed once per instrument until something succeeds, e.g. while the market is closed). A 401 logs in again; a lost WebSocket is reopened after 5 s. Run it with `./gradlew :Simulator:run` (uses `Simulator/simulator.json`) or `./gradlew :Simulator:installDist` and `Simulator/build/install/Simulator/bin/Simulator -config <file>`.

## Build and test

Use the Gradle wrapper (Gradle 9.2.1):

```bash
./gradlew build                                     # compile + test
./gradlew test                                      # all tests (JUnit 5 / Jupiter)
./gradlew test --tests 'com.hoddmimes.SomeTest'     # single test class
./gradlew test --tests 'com.hoddmimes.SomeTest.method'  # single test method
./gradlew :Server:test --tests 'com.hoddmimes.SomeTest' # test in the Server subproject only
```

Scope `--tests` to a subproject (`:Server:test`) once more than one project has tests; otherwise Gradle fails in the projects where the filter matches nothing.

Settings shared by all subprojects (Java plugin, group/version, repositories, JUnit 5) live in the `subprojects {}` block of the root `build.gradle`; a subproject's own `build.gradle` holds only what is specific to it, such as its dependencies. The shared settings include a Java 21 toolchain, matching the IntelliJ project setting, so the build does not depend on the JDK on the path (the machine default is JDK 25).
