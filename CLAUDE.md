# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Emporia is a marketplace system for trading commodities. Its focus is simplicity and pragmatism, so prefer straightforward solutions over elaborate abstractions.

The project is at an early stage. It is a multi-project Gradle build (group `com.hoddmimes`). The root project holds no code; it only aggregates the subprojects declared in `settings.gradle` (currently `Server` and `TestClient`), which use the standard `src/main`/`src/test` layout.

## Server architecture

`Server` (package `com.hoddmimes.emporia.server`) is a single-process marketplace server: a Javalin 6 web server backed by MongoDB. It was ported from EmporiaX: the Javalin setup, the login/authorization mechanisms, the complete admin interface and its database layer, the instrument cache, the matching engine and the bulletin board. EmporiaX's IPMC/TCP messaging was not ported.

- `Server` (main class) takes `-config <file>` and optional `-mode normal|test` (default normal), reads the JSON config (`Server/emporia.json`), connects `Database`, loads the `InstrumentCache`, creates and starts the `BdxDistributor`, creates the `MatchingEngine`, creates and loads the `BulletinBoard`, starts the `AuctionScheduler` and the `MarketStateScheduler`, and starts `RestApi`. The config holds `sessionInactivityTime` (`mm:ss`), `database` (host/port/name) and `http_interface` (`root` web dir, `interface`, `http_port` and/or `https_port` + `ssl.cert`/`ssl.key` PEM paths, served via the Javalin SSL plugin, HTTP/1.1 only: `ssl.http2 = false` in `RestApi`, because over HTTP/2 Jetty offers browsers WebSockets over HTTP/2 (RFC 8441), which Javalin doesn't recognize as an upgrade (it looks for `Sec-WebSocket-Key`), so `/ws` failed in the browser with 1006 while HTTP/1.1 clients such as the TestClient worked). `Server/emporia.json` uses http 8080 and https 8443 with `./cert.pem`/`./key.pem` (relative to `Server/`); the PEM files are git-ignored (`*.pem`) and must never be committed, and the server does not start without them while `https_port` is set.
- `RestApi` builds the Javalin app and registers each class in `endpoints/` implementing `RestEndpoint` (one class per route for login/session, one `Admin*Endpoints` class per admin resource); shared dependencies reach endpoints through `RestApiContext`. New endpoints are added to the list in `RestApi.declareEndpoints`.
- Authentication is HTTP-session based. A `before("/api/*")` filter requires the session attribute `admin-user` for `/api/admin/*` and `user` for every other `/api/*` path, except the login/session paths listed in `RestApi.PUBLIC_PATHS`. After it, a `beforeMatched("/api/*")` handler puts the trading user on the Javalin context as a `SessionUser` record (userId, firm) for every matched non-admin `/api` request whose session has one; endpoints read it with `SessionUser.of(ctx)` (null without a trading user). Trading users log in at `/api/login` with firm, userId and password; admins at `/api/admin/login`. One browser session can hold both logins, so each logout removes only its own attributes (`RestApiContext.logout`).
- `Server/WebContent` is the static web root, ported from EmporiaX. The trading client UI sits at the root (`index.html`, `login.html`, `market-view.html`, `css/tr.css`, `js/tr-session.js`). The admin UI is under `admin/` (`/admin` redirects to `/admin/login.html`), with every page and admin API call prefixed `/admin` and `/api/admin` so it doesn't clash with the trading UI. All admin pages are backed by endpoints. The trading `market-view.html` calls `/api/markets` and `/api/instruments?marketId=N` (`MarketEndpoints`, `InstrumentEndpoints`), which return only markets the user's firm is authorized for (403 for an unauthorized market). Authorizations are read from MongoDB on each request (`RestApiContext.authorizedMarkets`), not from the login-time `markets` session attribute, so admin changes apply at once. The page's `/ws` WebSocket (`bdx.BdxEndpoint`) pushes broadcast (bdx) messages, see below; the upgrade is rejected (401) unless the HTTP session has a trading user, the client may send `ping` (answered `pong`) and other client messages are ignored. `/api/logout` closes the WebSockets opened from that HTTP session, and so does the session timing out (an `HttpSessionListener` in `RestApi`). Jetty only detects timed-out sessions when its session housekeeper runs, so `RestApi` runs it every 30 s (or at the session timeout, if shorter) instead of Jetty's default 10 minutes. The WebSocket idle timeout is Jetty's default 30 s; the page's 25 s `ping` keeps an otherwise quiet connection open. The page lists the firm's authorized markets and, below them under their own heading in a teal color (`--bulletin` in `tr.css`), its bulletin markets (`/api/markets` and `/api/bulletin-markets`); a bulletin market shows its bulletins (`GET /api/bulletins?marketId=`, reloaded on each `Bulletin` message) instead of the price table. The page's Enter Order dialog follows the selected market: in a continuous/auction market it posts an order (`POST /api/orders`; instrument from the market's instruments, side, price and quantity required, price/quantity multiples of the instrument's `tickSize`/`lotSize`, market OPEN or PREOPEN), in a bulletin market a bulletin (`POST /api/bulletins`; free text instrument checked against the market's entries like `BulletinMarket.allows`, side required, price/quantity optional, market OPEN); it checks this before sending and shows the server's error with the HTTP status. A double click on a row of the price table opens the dialog for that instrument; on the bid it is prefilled as a SELL, on the ask as a BUY (trading against that side), with that side's best price and volume. A click on a bulletin opens an offer dialog (`POST /api/bulletins/{bulletinId}/offer`): instrument, the bulletin and the offer's side (the opposite) shown, price and quantity prefilled from the bulletin when it has them and required (quantity at most the remaining quantity), valid time in seconds (default 60) and an optional reference; not possible on the firm's own bulletin, one with a pending offer, or while the market is not OPEN. The top menu's Bulletin Orders splits the main area horizontally: above, the firm's own bulletins in all its bulletin markets (`GET /api/bulletins`, the `own` ones); below, the offers received on them that have not expired, with a countdown; a click on an offer opens an accept/reject dialog (`POST /api/bulletins/{bulletinId}/response`). It is reloaded on each `Bulletin` and `BulletinOffer` message; selecting a market leaves it. A `BulletinOffer` OFFERED with role OWNER (sent to every client of the bulletin owner's firm) shows a popup in any view ("New bulletin offer", with a countdown; Answer opens the view and the response dialog), removed when the offer is answered, expires or is cancelled. The page only uses `PriceUpdate`, `MarketState` (keeps the markets' `tradingStatus` current), `Bulletin` and `BulletinOffer` (popups, view reloads) and ignores the other message types; when a market is selected it also reads `GET /api/markets/{marketId}/prices`, used only for instruments that have no WebSocket prices yet.
- Broadcasts live in package `bdx` (EmporiaX's topic scheme and order book events, without its IPMC transport). `BdxMessage` is a JSON object starting with `type`, `topic` (`/<type>/<marketId>/<instrumentId>`, or `/<type>/<marketId>` for market messages), `marketId` and `instrumentId`, followed by its fields; prices and quantities are in display units (unlike the REST API's scaled longs). `BdxDistributor` sends a public message to every client whose firm is authorized for the market (resolved once when the client connects) and a private one only to the clients of its firm; it keeps the latest `PriceUpdate` per instrument and `MarketState` per market and sends them to a client when it connects. `publish` only queues a message; the distributor is a thread (`WsPublisher`, started by `Server`) that sends the queued messages, so the matching engine never waits for the clients. The WebSocket sends are asynchronous (Jetty queues them per session), so a slow client doesn't hold up the others; a client with more than 10000 unsent messages is disconnected (1008). Unit tests don't start the thread and call `dispatchQueued()` instead. Types: `PriceUpdate` (a full snapshot after each book change: best bid/ask price and volume, open, high, last, traded volume; JSON `null` clears a value), `MarketState` (published by the distributor itself on the cache's market state changes), `Trade` (anonymous: no firms), the anonymous order book events `AddOrder`/`ModifyOrder`/`RemoveOrder` (orderId, side, price, remaining quantity and the book's `seqNo`; a partial fill of a resting order is a `ModifyOrder`, a fully filled one a `RemoveOrder` with quantity 0; an incoming order that matches completely never rests and has no event), and the private `OwnOrder` (the same plus `event` ADDED/MODIFIED/REMOVED and `userRef`) and `OwnTrade` (one per side, to that side's firm, with side, orderId and `userRef`). The matching engine publishes all of them except `MarketState` from its orderbook callbacks. The bulletin board publishes market messages (`/<type>/<marketId>`, see below): public `Bulletin` and `BulletinTrade`, private `OwnBulletin`, `BulletinOffer` and `OwnBulletinTrade` (`BdxMessage.forFirm(type, marketId, firm)`).
- `Database` wraps MongoDB collections `Firm`, `User`, `Markets`, `Instruments`, `BulletinMarkets`, `Bulletins`, `Authorization` (firm → market, `*` = all markets, bulletin markets included) and `Admin`; MongoDB is the master store. A new market's `marketId` is the highest existing one + 1, over markets and bulletin markets together (`RestApiContext.nextMarketId`, so an authorization or bdx topic names one market), so a market can only be deleted once it has no orders and no instruments (a bulletin market once it has no bulletins); deletes are refused with 409. The admin can clear a market first: `DELETE /api/admin/markets/{id}/orders` (`MatchingEngine.deleteAllOrders`) and `DELETE /api/admin/bulletin-markets/{id}/bulletins` (`BulletinBoard.deleteAllBulletins`, state DELETED, a pending offer gets `BulletinOffer` event CANCELLED) delete everything in the market, of every firm, in any market state, overruling the authorization and trading status rules; the market and bulletin market pages have Delete All Orders / Delete All Bulletins buttons (otherwise a new market could reuse its id and inherit them). An `instrumentId` is a long with the `marketId` in the high 32 bits and a per-market sequence (from 1) in the low 32 bits; it is stored as a string. Passwords are stored as SHA-512 hex. A default admin `Admin`/`changeit` is created when the `Admin` collection is empty.
- `InstrumentCache` holds all markets and instruments in memory (ported from EmporiaX, without IPMC). `Server` loads it from MongoDB at startup and it is reached through `RestApiContext.instrumentCache`. Read markets and instruments from the cache wherever possible: the trading endpoints, market-existence checks, the `*` authorization expansion and new `marketId`/`instrumentId` allocation all use it. Only the admin list/get endpoints read MongoDB, because the admin pages need each document's `mongoId`. Every market/instrument write goes to MongoDB first; the endpoint then re-reads the document and calls `putMarket`/`putInstrument` (or `removeMarket`/`removeInstrument`), which notify `MarketCallbacks`/`InstrumentCallbacks` subscribers.

- The matching engine lives in package `me` (ported from EmporiaX's `me` module without IPMC; the bulletin board is in package `bulletin`; EmporiaX's generated request/response messages are replaced by the records `AddOrderRequest`, `OrderResponse` and `AuctionResult`). `MatchingEngine` keeps one `Orderbook` per instrument, created on first order: a CONTINUOUS book matches incoming orders immediately in price-time priority at the resting order's price, an AUCTION book only collects orders until `AuctionScheduler` triggers an uncross at one clearing price (max volume, then min imbalance, then closest to the last price, otherwise the lowest candidate). `AuctionScheduler` arms auctions at startup for the AUCTION markets in the cache, from each market's `open`/`close`/`auctionInterval`/`randomAuctionInterval`; markets or instruments added later need a restart. Prices and quantities are longs scaled by `MatchingEngine.SCALE` (100000), checked against the instrument's `tickSize`/`lotSize`. Orders and books are in memory only and are lost on restart. Each trade is also stored in MongoDB's `Trades` collection (`Database.saveTrade`; ids as hex strings, prices/quantities scaled, `tradeTime` as a `yyyy-MM-dd HH:mm:ss.SSS` string in server local time), and the engine reloads today's trades at startup (`Database.fromTradeDocument`) and replays them, oldest first, into the open/high/last/volume statistics of their order books (`MatchingEngine.restoreTrades`, creating the books, which stay empty of orders), then publishes a `PriceUpdate` per instrument, so the bdx snapshot and `/prices` show the day's prices after a restart. `MatchingEngine` takes the `Database`; the unit tests pass null, which skips storing and reloading. The engine's public methods are `synchronized`. An order's account is its firm, and a firm can only see, modify and delete its own orders. An order is only accepted (added or modified) while its market's `tradingStatus` is OPEN or PREOPEN and its instrument is not SUSPENDED (instruments are ACTIVE or SUSPENDED; the bulk load stores any other status, such as EmporiaX's OPEN, as ACTIVE), checked in `MatchingEngine` against the cache before the order reaches a book; deleting is allowed in every market state except CLOSED (also while the instrument is SUSPENDED). In PREOPEN orders are only put in the book, without matching; `MatchingEngine` subscribes to the cache's market state changes and, when a market changes to OPEN, uncrosses its continuous books once at a single clearing price (same algorithm as the auctions) before continuous matching takes over.
- Order entry (`OrderEndpoints`, `TradeEndpoints`): `POST /api/orders` (`instrumentId`, `side` BUY/SELL, `price`, `quantity`, optional `userRef`), `PATCH /api/orders/{orderId}` (`quantity`, optional `price`/`userRef`; a missing price or userRef keeps the order's current one, and a modify that increases the quantity or moves the price towards the other side replaces the order with a new `orderId`, returned in the response), `DELETE /api/orders/{orderId}`, and the firm's own `GET /api/orders` and `GET /api/trades` (optional `?marketId=` and/or `?instrumentId=`). Public market data (`MarketEndpoints`, firm must be authorized for the market, 403; unknown market 404): `GET /api/markets/{marketId}/trades` (today's trades in the market, oldest first, anonymous; optional `?instrumentId=`) and `GET /api/markets/{marketId}/prices` (a snapshot per instrument of the market, sorted by name, with the `PriceUpdate` fields scaled like the rest of the API; JSON null where there is no value, also for instruments without an order book yet). Trades are listed from the engine's memory (today's, reloaded at startup); bulletin trades are not included. The firm comes from the session; adding or modifying requires the firm to be authorized for the instrument's market (403), another firm's order is reported as not found (404), and engine rejections return 400 with `{"error":...}`. Order ids are hex strings.

- The bulletin board (package `bulletin`, ported from EmporiaX's `BulletinBoard`/`BulletinManager`/`BulletinEntry`, without IPMC) holds informal OTC bulletins in the bulletin markets. Bulletin markets are kept apart from the continuous/auction markets: collection `BulletinMarkets` (`BulletinMarket` record: `marketId`, `name`, `description`, `tradingStatus` OPEN/CLOSED/SUSPENDED, `open`/`close` times (required), `instruments`, `maxOrderTime` as `"hh:mm"`, hours may exceed 24, e.g. `"168:00"`), held by the `BulletinBoard` instead of the `InstrumentCache`, so the `AuctionScheduler` and matching engine never see them. The `MarketStateScheduler` (which takes the `BulletinBoard`) drives their status from `open`/`close` with the same rules as the other markets (no pre-open; closed at startup in normal mode, opened in test mode; SUSPENDED is set and lifted manually in the admin interface and never changed by the scheduler), writing through `Database.setBulletinMarketStatus` and `BulletinBoard.putMarket`. `Markets` only accepts the types CONTINUOUS and AUCTION. A bulletin market's `instruments` list (at least one entry) says what bulletins may be added for: an entry is a literal name matched exactly (case-sensitive), or a regular expression between slashes (`/Brent.*/`) that must match the whole instrument text. Admin: `AdminBulletinMarketEndpoints` (`/api/admin/bulletin-markets`, pages `bulletin-markets.html`, `create-bulletin-market.html`, `bulletin-market.html`), writing MongoDB first and then `BulletinBoard.putMarket`/`removeMarket`; `putMarket` publishes a `MarketState` for a new market and on each status change. `BulletinBoard` is one object for all bulletin markets (public methods `synchronized`); every bulletin is stored in `Bulletins` (`Database.saveBulletin`/`deleteBulletin`, without a pending offer) and reloaded by `BulletinBoard.load()` at startup, since bulletins can stay in the book for days. A bulletin gets `expiresAt` = add time + the market's `maxOrderTime` (a later change of `maxOrderTime` applies to new bulletins only) and is then removed with state EXPIRED, a pending offer expiring with it; bulletins that expired while the server was down are removed at load. `BulletinBoard` takes the `Database` (null in the unit tests: nothing stored) and publishes through a `Consumer<BdxMessage>` (`BdxDistributor::publish` in `Server`, a list in the tests). A bulletin has `marketId`, a free text `instrument` (no instrumentId), `side` BUY/SELL (required, unlike EmporiaX), optional `price`/`quantity` (0 = not given) and `userRef`; it is never matched. Another firm makes an offer (price, quantity up to the remaining quantity, optional `offerRef`, `validTime` seconds, default 60); a bulletin holds at most one pending offer. The owner's firm accepts it (a trade at the offer's price and quantity; the remaining quantity drops, and the bulletin is removed when it reaches 0 or had no quantity) or rejects it; an unanswered offer expires (a timer thread `BulletinExpiry`). Accounts are firms, as for orders: any user of the owner's firm may withdraw or answer, another firm's bulletin is reported as not found, and a firm can't offer on its own bulletin. Withdrawing is not allowed while an offer is pending. Adding, offering and accepting require the market to be OPEN; withdrawing and rejecting are always allowed. Bulletin trades are not stored in the database. Endpoints (`BulletinEndpoints`, firm must be authorized for the market, 403 otherwise): `GET /api/bulletin-markets` (the firm's authorized bulletin markets with their hours, instruments and `maxOrderTime`), `POST /api/bulletins`, `GET /api/bulletins` (optional `?marketId=`; everyone sees the public fields, the owner also `user`/`userRef` and a pending offer, the offering firm its own offer), `DELETE /api/bulletins/{bulletinId}`, `POST /api/bulletins/{bulletinId}/offer`, `POST /api/bulletins/{bulletinId}/response` (`accept` true/false). Prices and quantities are scaled longs in REST, display units in bdx. Bdx messages: public, anonymous `Bulletin` (`event` ADDED/UPDATED/REMOVED, `state` ACTIVE/OFFER_PENDING/TRADED/WITHDRAWN/EXPIRED/DELETED, `remainingQuantity`, `expiresAt`; price/quantity null when not given) and private `OwnBulletin` (the same plus `user`, `userRef`) to the owner's firm on every change; private `BulletinOffer` (`event` OFFERED/ACCEPTED/REJECTED/EXPIRED/CANCELLED, `role` OWNER with `userRef` or OFFERER with `offerRef`, the offer's side, price, quantity and `expiresAt`) to both firms; for a trade a public, anonymous `BulletinTrade` and a private `OwnBulletinTrade` (side, `userRef` or `offerRef`) to each side's firm. The firms are never told who the other side is. Bulletins are not part of the snapshot sent on connect; a client reads them with `GET /api/bulletins`.
- `MarketStateScheduler` drives each market's (and bulletin market's) `tradingStatus` from its market hours (server local time): on weekdays PREOPEN at `preOpenTime` (if set), OPEN at `open`, CLOSED at `close`; on Saturdays and Sundays markets stay CLOSED (only the close transition applies). It checks once a second whether a transition time was passed, reading the hours from the cache, so edits and new markets apply without a restart and a manual change in the admin interface stands until the next scheduled time. It writes through `Database.setMarketStatus` and `InstrumentCache.putMarket`, so OPEN triggers the matching engine's opening uncross. SUSPENDED is manual and never changed by the scheduler, in any mode. At startup in normal mode every OPEN market is set to CLOSED and has to be opened manually in the admin interface; `-mode test` overrides the scheduler: every market that is not SUSPENDED is set to OPEN at startup and the market hours are not applied (no transitions). `openAuctionTime` is not used, and the `AuctionScheduler` is independent of it.

Run it with `./gradlew :Server:run`, which uses `Server/` as working directory and `-config emporia.json` (for test mode: `./gradlew :Server:run --args="-config emporia.json -mode test"`); MongoDB must be running on the configured host. Logging is Log4j2, writing to the console and `server.log`. Every `/api` request gets an id from a counter (`r1`, `r2`, ..., restarting with the server), set in a `before` handler registered ahead of the auth filter: it is put in the Log4j `ThreadContext` under `rid`, so every line logged on the request's thread (endpoint, matching engine, database) shows it via `%X{rid}` in the pattern (`[]` outside requests and on other threads, such as the `WsPublisher`), and it is returned in the `X-Request-Id` response header; the last `after` handler removes it, since Jetty reuses its threads. Every `cLog.trace(...)` call is wrapped in `if (cLog.isTraceEnabled()) { ... }`, so its arguments are not built when trace is off; keep to that for new trace logging. The log configuration: `./gradlew :Server:run` and the IntelliJ `Server` run configuration pass `-Dlog4j2.configurationFile` pointing at `Server/log4j2.xml`; without it (e.g. tests) the built-in `src/main/resources/log4j2.xml` is used.

## Test client

`TestClient` (package `com.hoddmimes.emporia.testclient`) is a load/test program that uses only the REST API (Gson + `java.net.http`, no dependency on `Server`). It reads a JSON file (`-config <file>`, example `TestClient/testclient.json`) with `url`, optional `trustAllCertificates` (accept any HTTPS certificate, for the expired/self-signed ones) and `verbose`, and an array of `sessions`. Each session has `firm`, `user`, `password`, `repeat`, `txRate` (directives per second, 0 = unthrottled) and `directives`: `AddOrder` (`instrument` name or `instrumentId`, `side`, decimal `price`/`quantity` scaled by 100000 for the API, optional `userRef`; the `orderId` from the response is remembered under the `userRef`) and `DeleteOrder` (`userRef` of an earlier AddOrder; deletes that order by its `orderId`). Sessions run concurrently, each with its own HTTP session; a summary per session is printed (transactions sent/OK/failed and the average, median and 96% interval (2nd–98th percentile) of the transaction times) and the exit code is 2 if anything failed. With `-bdx true` (the default; `-bdx false` turns it off) each session opens a WebSocket to `/ws` with its own HttpClient (so it carries the session cookie) after logging in, waits for the reply to a first `ping` (the server answers it only after registering the connection, so no broadcast is missed), prints every broadcast message it receives (`[session] bdx: {...}`), sends `ping` every 25 s, and closes it 500 ms after its last directive; there is no subscription step, the server sends everything the firm may see. No session sends a transaction before all sessions have logged in and set up their WebSocket (a shared latch; a session whose setup fails still releases it). Run it with `./gradlew :TestClient:run` (uses `TestClient/testclient.json`) or `./gradlew :TestClient:installDist` and `TestClient/build/install/TestClient/bin/TestClient -config <file>`.

## Build and test

Use the Gradle wrapper (Gradle 9.2.1):

```bash
./gradlew build                                     # compile + test
./gradlew test                                      # all tests (JUnit 5 / Jupiter)
./gradlew test --tests 'com.hoddmimes.SomeTest'     # single test class
./gradlew test --tests 'com.hoddmimes.SomeTest.method'  # single test method
./gradlew :Server:test --tests 'com.hoddmimes.SomeTest' # test in the Server subproject only
```

Scope `--tests` to a subproject (`:Server:test`) once more than one project has tests; otherwise Gradle fails in the projects where the filter matches nothing.

Settings shared by all subprojects (Java plugin, group/version, repositories, JUnit 5) live in the `subprojects {}` block of the root `build.gradle`; a subproject's own `build.gradle` holds only what is specific to it, such as its dependencies. The shared settings include a Java 21 toolchain, matching the IntelliJ project setting, so the build does not depend on the JDK on the path (the machine default is JDK 25).

## Migrating code from EmporiaX

`../EmporiaX` is an earlier, similar project. Parts of its code will be migrated into Emporia over time.

- **`../EmporiaX` is read-only.** Never create, modify, delete or commit anything there, and never run commands that write to it, such as builds that produce output in its tree.
- **Migrate only on explicit instruction.** Copy or port only the code the user names. Don't bring over EmporiaX code proactively, even when it looks relevant.
- Reading EmporiaX to understand it or answer questions is fine.
